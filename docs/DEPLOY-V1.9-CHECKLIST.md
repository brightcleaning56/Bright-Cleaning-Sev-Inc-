## Before you click
- **Do not sync the existing `buildintel` blueprint.** Its service `buildintel-api` runs the old build, and syncing it
  would apply this file and may remove that service. Create a **new** blueprint instead, so the old service stays up
  as a fallback until the new one is verified.
- It creates paid resources: Postgres `basic-256mb` (`buildintel-db`), a Starter web service (`buildintel`), and a 5 GB disk.

## Steps
1. Render → **New +** → **Blueprint** → repo `brightcleaning56/Bright-Cleaning-Sev-Inc-`, branch
   `claude/buildintel-launch-requirements-i9bmnu`, file `render.yaml`. Name the blueprint `buildintel-v19`.
2. Fill in the prompted values:

| Variable | Value |
|---|---|
| `OWNER_EMAIL` | Your platform owner login email |
| `OWNER_PASSWORD` | A strong password you keep. It is the first sign-in. |
| `BACKUP_KEY` | 64 hex characters. Generate locally with `openssl rand -hex 32`. **Store a copy safely: without it, encrypted backups cannot be restored.** |
| `BASE_URL` | Leave for now. Set it to the service URL after the first deploy, then redeploy. |
| `SAM_API_KEY` | Leave blank unless you bid federal work. |
| `APP_SECRET` | Generated by Render. Do not change it after launch: it signs sessions and MFA. |
| `DATABASE_URL` | Filled in automatically from `buildintel-db`. |

3. Click **Apply** and wait for the build. The build runs `npm ci && npm test`.
4. When it is live, open `https://<service-url>/health`. Expect HTTP 200.
5. Set `BASE_URL` to the service URL, then redeploy.
6. Open `https://<service-url>/admin`, sign in with `OWNER_EMAIL` and `OWNER_PASSWORD`, and check the readiness page.
   Expect NO-GO until the owner items below are done.

## Known risk to watch
- The container runs as the `node` user, and the disk is mounted at `/var/data`. If Render mounts the disk owned by root,
  backups and plan-room uploads fail with EACCES. Check the logs after the first backup. If that happens, send me the log
  lines and I will fix the image.
